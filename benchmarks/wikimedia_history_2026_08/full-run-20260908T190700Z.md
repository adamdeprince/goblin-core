## Automatic verification and completion

After all feeds finish, the verifier reads each zset in **65,536-member rank
pages**, bounding server replies and client buffers for the full dataset.
The resulting ordered member/score stream is identical to single-reply
verification. This path was checked on the saved two-million-command input:
the complete result digest matched exactly, including the partial final page.
That preflight run is a verification check, not a new comparative timing.

Final checks compare all mapping digests, member counts, each representation's
tie ordering, integral scores and the expected **1,483,700,913** score sum.
The limited-run digest is deliberately not used as a full-run reference.
The controller rechecks the input checksum after the benchmark and records
the final status. A `run/COMPLETE` marker alone is not proof of a passing run;
check `JOB-PASS`/`JOB-FAILED`, `exit.status`, and `run/verification.txt`.

The job survives SSH disconnects in a detached tmux session. It does not
checkpoint/resume across a host restart and does not automatically retry.
Any new attempt must use a new project directory.
